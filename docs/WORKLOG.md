## 2. 分项记录

### 2.1 评测体系整改（commit 1）

**发现问题**：项目原本三项指标（Recall@1 / Recall@5 / 拒答准确率）全部是 **1.000**，
但换 embedding 后指标纹丝不动——说明评测本身没有区分度。排查出三处缺陷：

1. **检索集同义反复**：110 条题面 100% 原样包含目标文档标题，而打分公式中
   标题精确匹配占 0.60 权重，等于直接给出答案；
2. **重排权重过拟合该评测集**：语义信号只占 0.15，在口语化提问上损失约 30 个百分点；
3. **拒答是硬编码 17 词白名单**，与检索分数无关；原 44 条拒答样本**全部是负样本**，
   "永远拒答"即可满分。

**做了什么**：
* 重建 66 条口语化困难集（不含标题关键词）+ 48 条平衡拒答集（24 应拒 / 24 应答）
* 网格搜索重新标定混合检索权重 → 向量 0.70 / 关键词 0.10 / 标题 0.10 / RRF 0.02
* 拒答改为基于检索置信度（原始余弦）的阈值判定，经训练/留出拆分标定
* 清理死代码（`fused < min_score/100` 恒不成立）

**结果**：困难集 Recall@1 由 0.500 → 0.818；拒答准确率由 0.562 → 0.896，
领域内误拒由 18/24 降至 4/24。

### 2.2 阈值随语料漂移（commit 2 中的附带发现）

知识库扩容后（1102 字 → 4199 字），BGE 的可行拒答阈值区间从 `(0.409, 0.537)`
漂移到 `(0.489, 0.567)`，原阈值 0.47 落到区间外，拒答准确率从 0.958 跌到 0.771。

→ 据此建立约束：**任何知识库/分块改动之后必须重新标定阈值**（已写入配置注释）。

### 2.3 分块策略 A/B（commit 2）

原知识库每篇 55-171 字，**短于 chunk_size=400**，分块策略根本不产生差异——
所以先扩充为 11 篇结构化长文档（4199 字），实验才成立。

对比 3 策略 × 3 档 chunk_size × 2 provider × 2 评测集，BGE 在 v2 上 Recall@1：

| chunk_size | fixed | structure | structure_context |
|---:|---:|---:|---:|
| 200 | 0.818 | **0.833** | 0.803 |
| 300 | 0.742 | **0.788** | 0.773 |
| 400 | 0.773 | 0.773 | 0.773 |

**配对 bootstrap（4000 次）显示提升均未达显著**（95% CI 跨零）。
因此采用 `structure` 的依据是"不切断条款"的**结构性正确性**，
而非指标提升；`chunk_size` 保持 400 不因小样本最优值（200）调整。

反面案例：`structure_context` 把 v1 简单集刷到 1.000，却损害 v2 的块级区分度——
正是整改前项目状态的重演。

### 2.4 工具并发执行（commit 2）

原实现是顺序 `for` 循环，但系统 Prompt 与节点注释都写着"并行执行所有工具"。
改为 `asyncio.gather` + `asyncio.to_thread`，LLM 版与规则版共用同一套实现。

实测（3 次取中位数）：

| 场景 | 工具数 | 顺序 | 并发 | 加速 |
|---|---:|---:|---:|---:|
| 实时+预测（评测集多跳模式） | 2 | 0.353s | 0.357s | 0.99x |
| 三个重工具组合 | 3 | 3.038s | 2.529s | **1.20x** |
| 全部 10 个工具 | 10 | 3.034s | 2.561s | **1.18x** |

**收益低于直觉**：工具是 CPU 密集型（pandas/sklearn），线程池受 GIL 约束。
未改用进程池的原因：工具依赖模块级 DataFrame 缓存，多进程会各自重载数据与模型。

### 2.5 端到端评测（commit 3 + 5）

搭建 24 用例评测（8 政策 / 10 数据 / 6 超纲），作答器可插拔。
指标：工具路由、事实覆盖、引用正确、拒答合规、拒答—引用一致性、**幻觉引用**。

**发现的三类引用问题**（LLM 作答器实测）：
1. 编造库外标准号（如 `GB50011-2010`，不在本项目知识库）
2. 把标准号当条款 id 写进 `【依据：标题(GB3095-2012)】`（连模板里的"标题"都照抄）
3. 先正确拒答，又用自身知识补答并引用外部标准 → 拒答—引用一致性由 1.000 退化到 0.958

**关键结论**：引用安全应由代码保证——
`build_references()` 从工具结果**确定性提取**的 API 层引用，**幻觉始终为 0**；
而模型在自由文本里写的引用不可信。

改进方向（未实施）：模型只写正文，引用由代码注入；`refused` 时正文强制走固定拒答话术。

### 2.6 代码与数据审查（commit 6）

三层审查：静态阅读 63 个文件、脚本校验 4 份数据集、**实测 23 个 API 端点**。

修复 7 处问题（其中 1 处是本阶段自己引入的），最严重的是：
`main.py` 的 `get_rag_service()` 漏传 `chunk_strategy`，导致配置里的
`RAG_CHUNK_STRATEGY` 对 `/api/rag/search` **完全失效**（API 走 fixed、Agent 走 structure）。

数据审查结论：**4 份数据集全部通过完整性/唯一性/值域校验**
（52,704 行零缺失、零负值、零越界、零重复）。

详见 `docs/CODE_AUDIT.md`。

## 4. 待办与已知局限

### 待办（按优先级）

| 优先级 | 事项 | 说明 |
|---|---|---|
| 高 | **轮换 LLM API Key** | 该 Key 曾出现在对话记录中，建议在控制台重新生成 |
| 高 | 修 L1：合并两套 LLM 集成 | 见下 |
| 高 | 修 L4：容器内跑的是弱检索路径 | 见下 |
| 中 | 落实"引用与正文分离" | 报告 §9.4 已给出方案 |
| 中 | 降低规则版关键词路由的短板 | 当前 0.667，是端到端最大缺口 |
| 低 | 扩样重跑（检索 66→150、拒答 48→120） | 才能让分块结论达到统计显著 |

### 已知局限（详见 `docs/CODE_AUDIT.md` 第二节）

* **L1** 同时维护两套 LLM 集成（`llm_chat.py` 的 Dify/FastGPT 与
  `agents/orchestrator.py` 的 OpenAI 兼容），环境变量/降级策略/引用机制都不同
* **L4** Dockerfile 未装 `sentence-transformers`、compose 未设 `USE_REAL_EMBEDDINGS`
  → **容器内实际运行的是能力最弱的哈希检索路径**
* L2 两个 RAG 单例不共享索引（`/api/rag/reindex` 只重建其一）
* L3 `main.py` 的 `if __name__ == "__main__"` 位于文件中段
* L5 `/api/chat/agent` 为同步端点，LLM 调用期间占用线程池 worker（实测 ~11s/次）
* L6 拒答集有 3 条 query 取自检索集，正样本不够独立
* L7 `/api/feedback` 与 `/api/rag/search` 无前端入口
* L8 `engine.load_data()` 无缓存（调用方各自实现，重复 3 处）
* L9 `eval_agent` 的 60 条集合已迭代至 100%，是回归护栏而非能力度量
