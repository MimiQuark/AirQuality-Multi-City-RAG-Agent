# RAG 检索、拒答与执行效率评测报告

> 记录 2026-10 对 RAG 与 Agent 执行链路的系统性评测整改。
> 所有数字均由仓库内脚本实测产生，复现命令见文末。

---

## 0. 结论摘要

整改前，RAG 的三项指标（Recall@1 / Recall@5 / 拒答准确率）**全部是 1.000**。
排查后发现这组满分**不是能力，而是评测集与方法本身的问题**：多处缺陷叠加，
使指标失去区分度。整改后指标下降到真实水平，但**每一项都能追溯到具体样本**。

| 项目 | 整改前 | 整改后（BGE 语义模型） |
|---|---|---|
| 知识库 | 11 篇，每篇 55-171 字（≈1100 字） | 11 篇结构化长文档（4199 字） |
| 检索集 | 110 条，100% 题面照抄文档标题 | 66 条口语化提问，0% 含标题 |
| 拒答集 | 44 条，**全部**为"应拒答"，无正样本 | 48 条平衡集（24 应拒 / 24 应答） |
| Recall@1 | 1.000（**评测集同义反复，无意义**） | **0.773** |
| Recall@5 | 1.000 | **0.985** |
| MRR | 1.000 | **0.862** |
| 拒答准确率 | 1.000（**"永远拒答"即可满分**） | **0.896**（应拒 0.958 / 应答 0.833） |

> 注意：指标下降不代表能力下降。整改同时**扩充了知识库**（11 篇 → 4199 字，
> 每篇切成 2 块），检索任务本身变难了，前后不完全是同一道题。

---

## 1. 发现一：原检索集是"同义反复"，满分是必然的

`rag_cases.json` 的 110 条检索样本，实际只对应 **11 篇知识库文档**——
每篇文档配了 10 条**几乎同义的改写**：

```
rag-0 | HJ 633-2012 环境空气质量指数(AQI)技术规定        -> hj633-1
rag-1 | 请解释HJ 633-2012 环境空气质量指数(AQI)技术规定   -> hj633-1
rag-2 | HJ 633-2012 环境空气质量指数(AQI)技术规定的详细规定是什么 -> hj633-1
```

打分公式中**标题精确匹配占 0.60 权重**：

```python
rerank_score = 0.60 * title_score + 0.25 * keyword + 0.15 * vector + fused
```

题面原样包含文档标题 ⇒ `title_score = 1.0` ⇒ 直接锁定答案。

实测：**v1 集中 100% 的题面都包含目标文档标题原文**，v2 困难集中为 0%。
因此 `Recall@1 = 1.000` 衡量的是"题面是否照抄了标题"，不是检索质量——
它对 hash-v1 和 BGE 给出**完全相同**的结果。

---

## 2. 发现二：重排权重被这套评测集带偏

在困难集（口语化提问）上做权重消融，Recall@1：

| 打分方案 | hash (v1) | hash (v2) | BGE (v1) | BGE (v2) |
|---|---:|---:|---:|---:|
| **原公式** 标题0.60 / 词0.25 / 向量0.15 | 1.000 | 0.470 | 1.000 | 0.500 |
| 去标题，词0.50 / 向量0.30 / RRF | 0.291 | 0.576 | 0.945 | 0.773 |
| 纯 RRF 融合 | 0.373 | 0.636 | 0.564 | 0.742 |
| 纯向量余弦 | 0.291 | 0.515 | 0.936 | 0.803 |
| **新标定** 向量0.70 / 词0.10 / 标题0.10 / RRF0.02 | 0.882 | 0.561 | 1.000 | **0.818** |

原公式把语义信号压到 0.15，在真实口语化提问上让 BGE 损失约 **30 个百分点**。
它是在"题面照抄标题"的 v1 上调出来的，属于过拟合评测集。

---

## 3. 发现三：逐条过滤是死代码，且该机制本身无收益

```python
if fused < self.min_score / 100:   # min_score=0.15 → 阈值 0.0015
    continue
```

RRF 取值量级约 `1/60 ≈ 0.0167`，**恒大于 0.0015**——这行过滤永远不生效。

整改时先修成"相对下限"，再做参数扫描：

| min_score | hash v1 | hash v2 | BGE v1 | BGE v2 |
|---:|---:|---:|---:|---:|
| **0.00（关闭）** | **1.000** | **0.894** | **1.000** | **0.955** |
| 0.30 | 0.864 | 0.833 | 1.000 | 0.955 |
| 0.50 | 0.664 | 0.697 | 1.000 | 0.955 |
| 0.80 | 0.455 | 0.576 | 1.000 | 0.970 |

该机制对语义模型无收益（0.955→0.955），却把稀疏哈希模型从 1.000 打到 0.345。
数据不支持它，因此**默认关闭**，真正的闸门改由拒答置信度承担。

---

## 4. 发现四："低置信度拒答"实际是硬编码关键词白名单

```python
domain_terms = ("空气质量", "AQI", "IAQI", "PM2.5", ..., "预警", "标准", "限值")
refused = not (strongest and has_domain_term)   # ← 与检索分数完全无关
```

拒答判定只看提问里有没有预设词。后果：平衡拒答集上准确率仅 **0.562**，
**24 条领域内问题有 18 条被错误拒答**：

```
夏天下午在户外跑步会不会伤肺     ← 误拒，但库里 health-2 有答案
刮沙尘的时候怎么防护             ← 误拒，但库里 health-3 有答案
北方冬天为什么空气差             ← 误拒，但库里 season-1 有答案
```

原"拒答准确率 1.000"的来源也随之明确：原 44 条样本**全部**是负样本。

---

## 5. 整改：拒答改为基于检索置信度的阈值

置信度取**全库最高余弦相似度**（不用 `(cos+1)/2` 转换后的混合分：
该转换把无关文本的底噪抬到 0.5-0.6，阈值失去可解释性）。

标定：48 条平衡集分层拆为 24 训练 / 24 留出，在训练集上扫描阈值。

### 5.1 阈值随语料漂移（重要）

**知识库扩容后（1102 字 → 4199 字），BGE 的可行阈值区间从 `(0.409, 0.537)`
漂移到 `(0.489, 0.567)`。** 原阈值 0.47 落到新区间之下，导致拒答几乎失效
（准确率从 0.958 掉到 0.771）。

结论：**拒答阈值与语料规模、分块粒度强耦合，改动知识库后必须重新标定。**

### 5.2 重新标定结果（BGE）

| 阈值 (cos) | 准确率 | 应拒命中 | 应答正确 | 误拒数 |
|---:|---:|---:|---:|---:|
| 0.490 | 0.875 | 20/24 | 22/24 | 2 |
| 0.510 | 0.896 | 22/24 | 21/24 | 3 |
| **0.530** | **0.896** | **23/24** | 20/24 | 4 |
| 0.550 | 0.875 | 24/24 | 18/24 | 6 |
| 0.567 | 0.833 | 24/24 | 16/24 | 8 |

取区间中点 **0.53**：应拒命中 23/24、误拒 4/24、总体 0.896。
取中点而非样本内最优，是为了对语料变化更稳健；本项目"**宁可少答也不编造条款**"，
因此在同等准确率下偏向提高应拒命中。

### 5.3 离线 hash provider 无法承担语义拒答

对 hash-v1 分别用"原始余弦"与"混合分"两种信号扫描，**都不存在可行阈值**：

| provider / 信号 | 应拒均值 | 应答均值 | 可行区间 |
|---|---:|---:|---|
| hash-v1 / 余弦 | 0.191 | 0.227 | **无**（锚点冲突） |
| BGE / 余弦 | 0.439 | 0.601 | (0.489, 0.567) ✔ |

锚点冲突的具体表现：必须拒答的"建筑抗震设计规范怎么规定"得 0.337，
而必须应答的"雾霾天老人能出门吗"只有 0.184——**排序是反的**。

更极端的一组对照（2026-10-14 代码审查中实测）：

| 查询 | 是否领域内 | 离线 hash 余弦 |
|---|---|---:|
| PM2.5 的国家标准限值是多少 | 领域内 | **0.337** |
| 建筑抗震设计规范怎么规定 | 超纲 | **0.337** |

**语义毫无关系的两个查询得到完全相同的相似度**，说明哈希向量在该区间根本没有区分能力。

因此 CI 护栏对离线 provider **只设检索指标，不设拒答指标**。

## 6. 整改：分块策略 A/B

原知识库每篇 55-171 字，短于 `chunk_size=400`，**分块策略不产生任何差异**。
因此先把 11 篇条款扩写为结构化长文档（适用范围 / 术语 / 分级 / 限值 / 判定规则，
共 4199 字），分块策略才有可比性。

三种策略：

* `fixed` —— 原实现，按字符长度硬切（`step = size - overlap`），且会把换行压成空格，
  **结构信息完全丢失**；
* `structure` —— 按章节标题切分，相邻小节合并到不超过 size，单节超长时退化到句子边界；
* `structure_context` —— 在 structure 基础上每块前置文档标题。

BGE 在 v2 困难集上的 Recall@1：

| chunk_size | 块数 | fixed | structure | structure_context |
|---:|---:|---:|---:|---:|
| 200 | 29 | 0.818 | **0.833** | 0.803 |
| 300 | 22 | 0.742 | **0.788** | 0.773 |
| 400 | 14 | 0.773 | 0.773 | 0.773 |

### 6.1 统计检验：提升不显著

对 fixed → structure 做**配对 bootstrap**（4000 次重采样，按样本配对）：

| chunk_size | 差值 | 95% 置信区间 | 显著 |
|---:|---:|---|---|
| 200 | +0.015 | [-0.076, +0.106] | 否 |
| 300 | +0.045 | [-0.045, +0.136] | 否 |
| 400 | +0.000 | [-0.045, +0.045] | 否 |

**66 条样本的统计效力不足以确认这一提升。** 因此：

* 采用 `structure` 作为默认策略，理由是**结构性正确性**（不会从条款中间切断，
  保留章节边界；在 6 组配置中 5 胜 1 平，方向一致），**而不是宣称 Recall 提升**；
* 保留 `chunk_size=400`，不因 200 档的样本内最优去改默认值（避免过拟合小样本）；
* 把提升结论标注为"方向一致但未达显著"，并列入待扩样验证项。

### 6.2 一个反面案例：在坏评测集上"有效"的改动

`structure_context` 把 hash-v1 在 **v1 简单集**上的 Recall@1 刷到 **1.000**，
却在 **v2 困难集**上让 BGE 从 0.833 掉到 0.803。

原因：块内前置文档标题后，题面照抄标题的 v1 变成字符串匹配；而同一文档的多个块
因共享标题而彼此更相似，损害了块级区分度。

**这正是本项目整改前的状态**：改动只要迎合 v1 就会"看起来有效"。

## 7. 整改：工具并发执行

Agent 的系统 Prompt 与节点注释都写着"**并行执行所有工具**"，但原实现是顺序
`for` 循环，且 README 称 FastAPI 为异步、实际端点为同步 `def`。现改为
`asyncio.gather` + `asyncio.to_thread`，参数补齐逻辑下沉到
`backend/tools/implementations.py`，LLM 版与规则版共用同一套实现。

实测（`python -m backend.evaluation.bench_tool_parallel`，3 次取中位数）：

| 场景 | 工具数 | 顺序 (s) | 并发 (s) | 加速 | 省下 (s) |
|---|---:|---:|---:|---:|---:|
| A 实时+预测（评测集多跳模式） | 2 | 0.353 | 0.357 | 0.99x | -0.004 |
| B 政策+综合预警（规则版政策分支） | 2 | 1.422 | 1.426 | 1.00x | -0.004 |
| C 预测+综合预警+模型训练 | 3 | 3.038 | 2.529 | **1.20x** | 0.509 |
| D 全部 10 个工具 | 10 | 3.034 | 2.561 | **1.18x** | 0.472 |

**结论：并发收益低于直觉**，因为工具是 CPU 密集型（pandas / sklearn），
`asyncio.to_thread` 仍受 GIL 约束，只有释放 GIL 的数值计算段能真正重叠。
只有在**多个重工具同批调用**时才看得出差别；典型的 2 工具请求几乎没有收益。

**为什么不改用进程池**：工具依赖模块级 DataFrame 缓存
（`tools.implementations._df_cache`），多进程会各自重新加载数据与拟合模型，
启动成本超过并发收益。真正的收益点在于**工具从 CPU 密集型转为 IO 密集型之后**
（例如接入实时数据接口）。

## 9. 端到端评测：从提问到最终回答

前几节测的是检索与拒答，本节测**最终回答文本**——覆盖 LLM 环节特有的风险。
脚本：`backend/evaluation/eval_e2e.py`，24 个用例（8 政策 / 10 数据 / 6 超纲）。

### 9.1 指标定义

| 指标 | 含义 |
|---|---|
| 工具路由正确率 | 实际调用的工具集合是否与期望完全一致 |
| 事实要点覆盖率 | 回答是否包含工具结果里的关键事实 |
| 引用正确率 | 政策题是否引用了命中期望的真实条款 |
| 拒答合规率 | 超纲问题是否拒答、领域内问题是否未被误拒 |
| 拒答—引用一致性 | 检索判定 refused 时，回答不得引用任何条款 |
| **幻觉引用数** | 回答中出现的条款 id / 标准号是否在知识库中**不存在** |

### 9.2 实测结果：规则版 vs LLM 版

作答器：规则版（离线编排）vs LLM 版（LangGraph + 智谱 `glm-4-flash`）。
两者共用同一套 BGE 检索层，差异只来自编排与回答生成。

| 指标 | 规则版 | LLM 版 | 变化 |
|---|---:|---:|---|
| 工具路由正确率 | 0.667 | **0.875** | ↑ +20.8 |
| 事实要点覆盖率 | 0.583 | **0.958** | ↑ +37.5 |
| 引用正确率（**回答文本**内） | **0.750** | 0.542 | ↓ −20.8 |
| 拒答合规率 | 0.875 | **0.917** | ↑ +4.2 |
| 拒答—引用一致性 | **1.000** | 0.958 | ↓ −4.2 |
| 幻觉引用数 / 总引用数（文本） | **0 / 12** | **6 / 24** | ↓ 出现幻觉 |
| └ 其中编造条款编号 | 0 | 1 | ↓ |
| **API 层结构化引用正确率** | 0.750 | **0.917** | ↑ +16.7 |
| **API 层结构化幻觉引用** | **0** | **0** | — |

### 9.3 三个结论

**① LLM 编排显著提升了"会不会用工具"，这正是规则版的最大短板。**

规则版 8 个政策题有 7 个因题面不含"标准/规定/限值"被路由到数据工具；LLM 版
把其中大部分纠正过来，工具路由 0.667 → 0.875，事实覆盖 0.583 → 0.958。

**② 但回答文本里的引用质量明显下降，出现了三类问题。**

```
[编造库外标准号] Q: 建筑抗震设计规范怎么规定（超纲题）
  A: 未检索到相关标准条款，以下仅基于一般知识回答。
     建筑抗震设计规范通常包括……（引用了 GB50011-2010）
  → 模型先正确拒答，然后又用自身知识补了一段无关内容，并引用了库外标准号

[把标准号当条款 id] Q: 成都最近一周的 AQI 走势（数据题）
  A: 根据《环境空气质量标准》（GB 3095-2012）【依据：标题(GB3095-2012)】
  → 连提示词模板里的"标题"两个字都照抄了，且用标准号冒充条款 id
```

**拒答—引用一致性从 1.000 退化到 0.958**：模型明明判定"未检索到相关条款"，
却又给出内容并引用外部标准，这对用户而言比直接拒答更危险。

**③ 但 API 层的结构化引用完全干净：0 处幻觉，正确率 0.917（高于规则版）。**

原因是 `orchestrator.build_references()` 从工具结果**确定性提取**引用，
不依赖模型是否遵守输出格式。也就是说：

> **系统的引用安全由代码保证，而模型在自由文本里写的引用是不可信的。**

### 9.4 由此得到的改进方向

不要在回答文本里让模型自己写引用，而应改为**代码注入**：

1. 模型只负责生成正文；
2. 引用由 `build_references()` 从工具结果提取后，由渲染层统一附加
   （或直接由后端返回结构化 `references` 字段交由前端展示）；
3. 检索判定 refused 时，正文强制替换为固定拒答话术，不进入模型生成。

这样既保留 LLM 的编排能力（路由 +20.8 点、事实覆盖 +37.5 点），
又保住规则版的可追溯性（一致性 1.000、幻觉引用 0）。

### 9.5 运行条件与稳定性说明

* 模型：智谱 `glm-4-flash`（该账号可用的免费档；`glm-4.5` 及以上返回
  `429 余额不足或无可用资源包`）。`glm-4.7-flash` 虽免费但为推理模型，
  单次约 40s、输出 3000+ tokens 且不稳定，故未采用。
* **LLM 输出具有非确定性**：三次运行的工具路由稳定在 0.875，
  但事实覆盖在 0.958~1.000、文本引用正确率在 0.542~0.667 之间波动。
  表中数据为其中一次完整运行，**结论应以"量级差异"为准，而非精确到小数点**。
* 延迟：LLM 版单问题约 11s（规划 + 综合两次调用），规则版约 0.2~1.4s，
  相差约一个数量级。这是 LLM 编排的固有代价。

## 10. 诚实边界

1. **知识库仍只有 11 篇文档**，检索本质是 11 路分类，绝对指标偏高。
2. **v2 拒答集 48 条、检索集 66 条均为自建样本**，统计效力有限
   （第 6.1 节的 bootstrap 已经显示部分结论无法达到显著）。扩样前，
   报告中的小幅差异应视为噪声。
3. **分块策略的收益未达统计显著**，采用 structure 的依据是结构性正确性，不是分数。
4. **拒答阈值与语料强耦合**（第 5.1 节），任何知识库/分块改动之后都要重新标定。
5. **离线 hash 的指标不代表线上能力**，它只用于 CI 回归。
6. **端到端评测只用了单一模型单次运行**：LLM 侧为非确定性输出，第 9.2 节的
   文本引用类指标在不同运行间有波动，尚未做多次取平均。
7. **端到端用例 24 条**，样本量小；小幅差异（如拒答合规 0.875→0.917）应视为噪声。
8. **未评测 LLM 版的成本**：本报告只记录了延迟数量级，未统计 token 费用。

## 11. 复现方式

```bash
# RAG 评测（离线，CI 路径）
python -m backend.evaluation.eval_rag

# 两套评测集 x 两种 embedding 对比 + 拒答阈值扫描
pip install -e ".[rag]"
set USE_REAL_EMBEDDINGS=1      # PowerShell: $env:USE_REAL_EMBEDDINGS="1"
python -m backend.evaluation.eval_rag --all --sweep

# 分块策略 A/B（3 策略 x 3 种 chunk_size x 2 provider x 2 评测集）
python -m backend.evaluation.bench_chunking

# 工具并发基准
python -m backend.evaluation.bench_tool_parallel

# 端到端评测（规则版基线；配置 LLM_API_KEY 后可跑 --answerer both）
python -m backend.evaluation.eval_e2e

# 全量质量流水线
python scripts/record_checks.py
```
